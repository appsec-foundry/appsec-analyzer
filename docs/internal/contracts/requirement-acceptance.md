# Requirement acceptance contract

This contract contains the detailed acceptance rules for the [user requirements](../../../requirements.md). Both documents are normative: shortening the user catalog does not relax these rules. The rules describe intended behavior, not proof of implementation or live qualification. The [bindings](../../../data/requirement-bindings.yaml) identify relevant producers, consumers, and partial test evidence.

Keep these rules aligned when changing a user outcome. Record semantic changes in a proposal and update its bindings. Existing schemas and domain contracts still govern their respective implementation boundaries. The [ID migration](../../../specs/changes/plain-requirement-ids/proposal.md) records the origin and redistribution of these rules.

## REQ-001: Scan without an AI account

Offer a deterministic source scan that needs no model account or model budget. Show its coverage, exclusions, and unverified observations, and clearly state that a complete security assessment was not run.

## REQ-036: Get a quick security indication

Offer `score REPO` for one top-level local Git checkout or explicitly selected supported Git URL, without model calls or writes into the target. Reuse Analyzer source admission, private redacted snapshots, source-change detection, and bounded remote retrieval. Treat repository content as data and sanitize diagnostic and terminal fields. Record source revision, captured state, public interface version, and source-policy identity in structured results. Unlike the source scan and assessment report (REQ-001, REQ-003), omit excluded-file lists and counts from the score output in every format; retain source admission and exclusions internally.

Use the retained version-2 scoring calculation over route inventory, architecture coverage, configuration/IaC, and source-auth scanners. Report per-indicator scores and applicable coverage; keep findings from unscored indicators visible and identify excluded severities. A headline requires at least five applicable coverage rules and complete, validated results from every required scanner. Otherwise return `undetermined` or `incomplete` with a null headline score and visible findings and warnings. Report scanner observations as unverified and state that this is a limited quick check without exposure context, not a full assessment or security approval.

Offer readable text and mutually exclusive JSON/YAML output conforming to the score schema. The score help must explain local and supported Git URL inputs, reuse of the existing Analyzer engine without model calls, the 0-100 score and its limited scope, progress/result streams, and local/remote examples. Describe runtime as dependent on source size, scanner work, and Git retrieval rather than asserting an unmeasured completion deadline; keep the README, score guide, and installed entry skill aligned.

Organize the text summary into an overall score and coverage, an aligned area table, numbered top findings with example locations, warnings, and a short examined-source footer. Highlight the headline score in a separated block while retaining the limited-check qualifier next to it. Reuse the shared Analyzer terminal palette for score bands, severity labels and totals, headings, and secondary finding metadata. Apply color to progress status tokens: cyan running, green done, red failed/invalid, and yellow missing/cancelled, while keeping descriptions and durations neutral. Auto-detect color independently for stdout results and stderr progress, honor the shared NO_COLOR/FORCE_COLOR policy, and always keep JSON/YAML free of styling codes. Separate findings with blank lines, wrap complete check titles to the available width, and put the example location and repetition count below each title. Public finding titles are not truncated to the retained script's legacy 50-character display limit; keep the direct script's default unchanged. Rank areas weakest first only for scored runs; incomplete or undetermined runs show every area as unscored. Keep unscored findings and excluded severities prominent, and retain detailed control signals and comparison fingerprints in structured output.

Start with an immediate, flushed `Calculating security score for ...` header naming the operator-selected repository before runtime preparation, grouped into repository preparation, security checks, and the result. Give runtime loading, repository reading and snapshot preparation, every required scanner, calculation, and source validation separate persistent status lines under the three phase headings. Interactive stderr refreshes only the running step with elapsed time; completed steps retain their status and measured duration, and a final summary shows total time. A scanner line must distinguish complete validated output from failed execution, missing output, and invalid output; do not mark a failed scanner done or equate completed execution with absence of vulnerabilities. Redirected stderr and terminals without cursor support receive plain step start/completion lines without animations or control characters. Keep Git cloning visible when applicable. Stop the live display on success, incomplete scans, errors, and interruption; label incomplete or stopped work accordingly without implying that security checks passed. Send progress only to stderr and reserve stdout for results, including when either stream is piped. Only the explicitly selected repository identity may appear in progress: show its expanded local path or Git host/project, strip URL user information, queries and fragments, reject control or formatting characters, and bound the displayed label. Keep that identity on the existing heading or repository line; emphasize the project segment with bold accent text and mute its prefix without removing or rearranging the sanitized identity. Do not echo source contents, other filenames, or credentials.

Exit 0 for a computed score regardless of value, 2 for insufficient coverage or invalid arguments, 1 for incomplete execution or operational errors, and 130 for user cancellation. Ctrl+C during preparation, scanning, or source validation must finish the status with a cancellation message, publish no result, and unwind temporary source and checkout cleanup without a traceback. Invalid local source selections and incomplete scanner output must identify the failure and a recovery action without raw exception, scanner, credential, or source details. Contain unexpected score runtime and rendering errors with a safe operational diagnostic; serialize the result before declaring completion and publishing it. A closed output pipe exits 1 without a traceback; already delivered output cannot be withdrawn. Invalid arguments and operational errors can omit the result document. Do not introduce an implicit score-based CI gate.

Scores are comparable only across commits of one repository with matching scoring version, catalog fingerprint, applicable-coverage fingerprint, and source policy. Preserve the retained direct script's result shape and distinguish it from public results captured through the Analyzer boundary.

## REQ-038: Check platform security settings

Offer a command, separate from `assess`, `scan-sources`, and `score`, that checks security-relevant settings of one GitHub or GitLab repository selected explicitly by Git URL. Make no model calls, analyze no source code, and send only read requests; write nothing to the target repository or its platform. Use the same check implementation in this command and in the scan phase.

Run at least the checks in the [platform security settings table](platform-security-settings.md): required reviews and blocked force pushes on the default branch, secret scanning, push protection, read-only default workflow token permissions, no workflow approval of pull requests, and approval for runs from forks. The table maps each check to its platform sources and says where a platform has none. Each check has a stable `PLATSEC-NNN` ID that keeps its meaning and is never reused; every result names it. Report repository visibility as context, not as a check. Other settings, such as administrator access, webhooks, and deploy keys, are out of scope until listed in the table.

Report each setting as `set`, `not set`, or `not checkable`. Give every `not checkable` result a reason: missing permission, feature not offered by the platform or plan, platform error, or not applicable. Never count an unreadable setting as `set`. Treat a response that cannot distinguish an absent setting from a denied read, such as a not-found answer, as `not checkable` unless the access level makes it unambiguous. Treat a missing field or an empty result that the platform also returns for insufficient access as `not checkable` with the reason missing permission, never as `not set`. `set` means the setting is configured, not that it works or that bypasses are absent.

In `assess`, run the check as the Platform Security Settings phase after source admission and before Reconnaissance, once per repository supplied as a supported GitHub or GitLab URL. Never derive a platform or repository from repository content such as Git remotes. For a local repository, show the phase as skipped with the reason and how to enable the check, and send no platform request. In a combined scan, report the outcome per repository (REQ-007). Keep the numbers of existing stages unchanged. Record the result and check time with the run; a resumed run reuses them instead of querying the platform again.

Provide the results to the Controls and STRIDE phases as platform-setting evidence that names the check ID, state, reason, repository, check time, and access level. This evidence has no source location. It can support or contradict a control (REQ-006) and inform a finding's severity (REQ-009), but it is not a finding by itself and does not replace the target-source evidence a finding needs (REQ-008). Treat `not checkable` and a skipped phase as unknown; never infer missing or present protection from them. Pass only check IDs, states, reasons, and other allow-listed values to model roles; keep free text returned by the platform, such as rule names or descriptions, out of model context.

Without a token, check only publicly readable data. Use a token only when the user supplies it explicitly for the invocation, and require it to be read-only. Do not take credentials from repository content, from ambient CLI sessions, or from analyzed files. Send the token only to the selected platform host, refuse redirects to another host, and keep it out of the analyzed repository, model context, run state, results, logs, diagnostics, and structured output (REQ-032). Before the first request, state the platform host and that the token is sent there, and distinguish this from model transmission and Git retrieval (REQ-033).

For the command, offer readable text and mutually exclusive JSON/YAML output. In a scan report, list all results in a separate section. Record platform, repository, visibility, check time, and access level (anonymous or token, without the token value). State that the settings reflect check time while the source reflects the examined revision, and that the results are neither an assessment of the code nor a release approval.

Intended and negative cases cover a missing permission, an ambiguous not-found answer, a response that omits a field because access is insufficient, a redirect to another host, token redaction, an unsupported platform, an unreadable setting that must not appear as `set`, a local repository that sends no platform request, a Git remote that does not trigger the check, a `not checkable` result that the analysis does not treat as missing protection, and platform free text that does not reach model context.

Every check ID needs at least one test that expects `set` and one that expects `not set` or `not checkable`, each referencing the ID. A catalog test fails when a check ID lacks either case.

## REQ-042: Find leaked secrets

Offer `scan-secrets` for one top-level local Git checkout or explicitly selected supported Git URL, separate from `assess`, `scan-sources`, and `score`. Reuse Analyzer source admission and bounded remote retrieval, write nothing into the target, and keep results outside the analyzed repository (REQ-035). Scan the files of the examined revision; scanning Git history is not part of this requirement. Report excluded paths with their reasons so that a scan without hits is not mistaken for full coverage, and state that a scan without hits does not prove the source is free of secrets. Using the results in `assess` needs a separate decision.

Scan with Analyzer's own scanner, which runs on the linear-time RE2 regular expression engine through the `google-re2` package. Offer the package as an optional installation extra so that the other commands install and run without it; when it is missing, stop with the exact installation command and never fall back to Python's own regular expression engine. Use the provider-specific rules of the Gitleaks default rule set as base rules: rules that recognise a credential by a provider's token format or by the provider's name next to a value of fixed form. Leave out the generic rule that reports any high-entropy value after a word such as key or token; credentials without a recognisable format are left to the model review. Package the base rules as a copy from a reviewed Gitleaks release with its MIT license text, and record that release with each result. Apply each rule's keywords, regular expression, secret group, entropy threshold, path condition, and the allow-lists and stop words that the packaged rules define. If a packaged rule does not compile, stop instead of skipping it. Decoding encoded values such as Base64 or hex is not part of this requirement. Apply rules that check only the path to every file, including binary files; then skip binary files and files above a documented size limit, and report them as excluded. Never read scanner configuration, ignore files, or baselines from the analyzed repository. A hit on a line that carries an inline allow marker such as `gitleaks:allow` stays visible and is labelled as marked allowed by the repository.

Version and package Analyzer's maintained rules, which add to the base rules, with fixtures that match and fixtures that must not match. Like a base rule, a maintained rule needs a provider's token format or the provider's name next to a value of fixed form. Updating the copy of the base rules is a reviewed change that checks that every rule compiles and runs all fixtures. Model help when writing rules does not replace that review.

Accept own rules in the Gitleaks rule format with an ID, a regular expression, and optional keywords and entropy threshold, from three sources: files in `secret-rules/` under the documented XDG configuration directory (by default `~/.config/appsec-analyzer/secret-rules/`), a file selected with `--rules FILE`, and files that the selected organization profile lists under `secret_rules`, relative to the profile. Select the organization profile with `--org-profile`, disable it with `--no-org-profile`, and apply an organization distribution's bundled profile as `assess` does (REQ-018). Reject rule files inside an analyzed repository and never read rules from repository content. Combine the rules of all sources. Before scanning, check that every own rule compiles in RE2, has an ID that is unique across all sources and does not collide with a maintained rule, and contains no allow-list; otherwise stop with an error that names the rule and its source instead of skipping it. Own rules only add hits. Record which own rules were active with their source, and which rule produced each hit.

Report each hit with its rule, file, line, a masked value, and a stable fingerprint shared by all locations of the same value. A masked value keeps at most four leading characters, none for values shorter than 16 characters, and the length. Never write a secret value into results, logs, diagnostics, terminal output, or structured output (REQ-032). Offer readable text and mutually exclusive JSON/YAML output. Results are advisory; the exit code signals failure only when the user explicitly selects a gate (REQ-022).

Make no model call unless the user selects `--review`. Before the first call, state the model host, the model, what is sent, and the call or spending limit (REQ-023, REQ-033). The model gets no tools and no file access; it sees only what Analyzer sends. Send only bounded context windows around hits and deterministically selected candidate code, such as lines with credential names, connection strings, or authentication calls. Mask every literal value in that content, such as string literals and configuration values, and every high-entropy token elsewhere, keeping only the length, the character class, and the leading characters allowed above. For each masked value, add only features that Analyzer derives locally from the real value: whether it equals a known example value, whether it contains a word such as example, test, or dummy, whether it consists only of repeated characters or sequences such as 1234, and whether its randomness is low, medium, or high. Send no other part of the value. After masking, run Analyzer's secret detector and the active scanner rules again, and send nothing that still matches.

For each hit, the model returns one category: likely real, test or example value, placeholder, public by design, or unclear, with a reason, what the credential could give access to, how exposed it is, and what to fix. Validate each reply against a strict schema with these fixed categories; an invalid reply leaves the hit unreviewed. A review only labels a hit and can lower its confidence; it never removes or hides a hit. State that the model's judgement is not proof. Never use a found credential, send it to its provider, or test it against any service.

Report locations that the model names as missed credentials separately from scanner hits, as model-reported candidates, after checking that the file and line exist in the examined source. The model writes no patterns: for a missed credential it names only the location, the likely provider, and keywords. Analyzer derives a proposed rule locally from the real value, from its leading characters, its character class, and its length. The pattern contains at most the leading characters that a masked value may show, so a value shorter than 16 characters gets no proposal. Check each proposal deterministically: it compiles in RE2, matches the location it was proposed for, contains no allow-list, and stays below a match limit on the examined source. Write accepted proposals to the result in the own-rule format. A proposal takes effect only after the user adds it to their own rules; model output never changes active rules, allow-lists, or the scanner configuration.

Intended and negative cases cover a missing RE2 package that stops the scan without falling back to another engine, a packaged rule that does not compile, a value that only the left-out generic rule would report, a binary or oversized file that is reported as excluded, a binary key file that a path rule still reports, repository configuration, an ignore file, and an inline allow marker that must not hide a hit, an invalid own rule that stops the scan, an own rule with an allow-list, a secret value that must not appear in any output, model input that contains no unmasked literal value and no part of a value beyond the allowed leading characters and features, a review in which the model has no tool or file access, a scan without `--review` that makes no model call, an invalid model reply, a review that must not remove a hit, and a rule proposal that does not compile, misses its location, matches too broadly, or would contain more of the value than the allowed leading characters.

## REQ-002: Choose what to assess

Let users select local Git repositories or supported Git URLs, combine repositories into one assessment, choose analysis depth, and select a separate result directory. Reject unsupported component or directory restrictions instead of silently analyzing a different scope.

## REQ-003: Know what was examined

Record source revisions, captured source state, context sources, exclusions, and coverage gaps. Keep conclusions within the examined snapshot and reject source changes that would invalidate its evidence.

## REQ-004: Find relevant security risks

The survey examines every assessed component for all six STRIDE threat categories at every depth. Include applicable identity, authorization, input, cryptography, secrets, browser, deployment, supply-chain, and AI security concerns; make incomplete coverage visible. Cover implementation weaknesses and insecure design assumptions; explain that source analysis cannot prove production behavior or approve a release.

Run the deterministic source, configuration, and architecture-coverage rules on every assessed repository before the evidence review of the threat analysis. Pass each rule hit that cites a source location to the same evidence review as survey findings and report it only when that review confirms it; a rejected hit never becomes a finding. Treat application-wide hits, such as high-confidence architecture anti-patterns and confirmed architecture hypotheses, like hits at a single code location. A finding from a rule hit names its rule. Make no review call for this purpose when no rule hits.

## REQ-040: Verify security aspects item by item

Define each catalog verification item in versioned YAML that Analyzer owns and packages, with a stable ID, aspect, STRIDE tag, CWE, mode, objective, deterministic applicability, starting points from scanner rules and facts, guidance, matching control catalog entries, required evidence, deterministic post-checks, and fixtures. Repository content cannot define, select, or disable catalog verification items.

A verification item asks whether one security property holds within a component, at every place where it matters; a path through several weaknesses or a rule of the application's business flow is an abuse case (REQ-011).

Map every shipped scanner rule to a verification item as a starting point, or record why a rule has none. A verification item in rules mode takes its outcome from its rules and makes no model call unless the operator enables a context review, which cannot remove a finding.

Pre-checks provide starting points, not limits. Within the verification item's objective and a bounded search, the model may reject candidates with evidence, add its own, and follow data flows beyond them; each candidate records whether it came from a pre-check or the model. Weaknesses found while working on a verification item belong to the matching verification item or are reported as outside the verification catalog.

Record exactly one outcome per verification item and component, or per repository for verification items that examine repository-wide configuration: finding, control, partial, no finding, undecidable, not applicable, or disabled. Record for each outcome how many candidate locations it covered. Report control only when every candidate location has an evidenced control, and partial when only some have. Only control counts as a confirmed control; a partial, no finding, unchecked, undecidable, or disabled verification item is never reported as a control.

Post-checks are fixed functions with validated parameters and return confirmed, contradicted, or not verifiable. Model output never supplies executable patterns, queries, or code. A contradicted claim becomes undecidable with the reason. A claim that no post-check can verify keeps its outcome and is labelled as evidenced by model review only, unless the evidence review confirms its finding.

A control requires enforcing code or configuration at a cited location and no contradicting post-check. Comments, documentation, and controls outside the examined sources are not control evidence and leave the question undecidable. A control that no post-check confirms, or whose candidate set only the model defined, is labelled model-evidenced and is prioritized for evidence verification. A finding from a deterministic rule is removed only when a post-check confirms the control; otherwise it remains and records the disagreement. Report control and partial results in the existing control posture under their matching control catalog entries; verification results do not create a second control view.

Run an open review per component after the verification items. It receives their results and the confirmed business context and reports evidence-supported weaknesses that no verification item covers, under the same evidence rules. Reserve a share of the model budget for the open review so that verification items cannot consume it. The model may derive application-specific verification items from business invariants it identifies; they receive run-specific IDs, use the same outcomes and evidence rules, run only fixed post-checks, and cannot disable, replace, or change catalog verification items.

Show verification progress in the live progress and outcome counts in the completion summary. In the report, link each finding to its verification items and rules, or mark it as found outside the verification catalog, through a self-contained appendix that lists every verification item, its outcome per component, and every disable reason. Retain verification item and rule IDs in YAML and SARIF.

Operator-owned scan profiles can disable a verification item only with a reason. Organization profiles can mark verification items as required; a conflicting disable refuses the run before any model call. Disabling never suppresses a finding that another source supports, including the rule findings of a disabled rules verification item; such a finding notes the disabled verification item and its reason.

Which security aspects are verified is one of the depth settings that REQ-018 describes. Before the survey starts, the assessment names the components it will verify. Before the first verification job runs, it says whether the remaining budget covers all of them. The live progress shows one step per verified component, however many jobs it needs. An aspect that could not be verified completely is marked as incomplete.

The survey keeps running for all aspects. Verification findings join the findings register together with the survey's and the scanners' findings and receive IDs, priorities, and mitigations like them. If verification finds a weakness on the same code line as a survey or scanner finding, with the same CWE or a CWE of the same weakness family, the report shows one finding and names each method that found it, whatever threat categories the methods assigned. Findings on neighbouring lines stay separate, because neighbouring lines often register different routes, and so do verification findings about different routes registered on one line. A refuted finding never absorbs a verification finding. If verification shows that a location reported by the survey is protected, the survey finding stays in the report and is marked as contradicted, so that a reader can check it.

A combined finding keeps every location, verification item, and scanner rule of its parts, and its severity is not lower than that of its most severe part. It takes the evidence review verdict of its reviewed part. A model rewrites its description and remediation from the texts of all parts; the model receives only these finding texts and their locations, and the code keeps the locations, severity, IDs, and methods. If the model call fails, the budget does not cover it, or the rewritten text drops a part's location, the finding keeps the text of its most severe part and lists the remediation steps of all parts.

A verification finding that no evidence review covers and no post-check confirms, including a finding outside the verification catalog, goes to the evidence review after verification. A finding already confirmed, or already reviewed as part of a combined finding, is not reviewed again. A finding the review confirms is scored and counted like a confirmed survey finding. A finding the review rejects stays in the findings register, marked as contradicted by the evidence review and unscored, so that a reader can check it. A finding the review leaves open, or that the budget leaves unreviewed, stays labelled as evidenced by model review only and unscored; a budget shortfall is reported as a gap. Without such a finding, the run makes no review call for this purpose.

## REQ-005: Understand the architecture

Describe valuable assets, actors, components, interfaces, data flows, and trust boundaries.

## REQ-006: Understand security controls

Distinguish evidenced, broken, missing, uncertain, and inapplicable controls. Declarations or an absence of findings must never establish that a control works.

## REQ-007: Keep repository origins clear

Retain repository provenance in combined results and require evidence from both sides for cross-repository connections. Clearly identify imported reference models as context; importing one must not imply that its repository was scanned.

## REQ-008: Show the evidence behind each finding

Explain each concrete security problem with target-source evidence, affected scope, and distinct instances. Group shared weaknesses without losing individual findings. Keep unproven claims visibly unproven and unscored; revalidate imported known threats or record mitigation, declared acceptance, or skip reasons.

## REQ-009: Explain severity

Base severity and scores on supported security impact and policy limits. Business context may clarify impact and order findings within a priority tier, but must not invent findings, raise likelihood, change tiers, or relax caps. Distinguish unknown impact from an explicit absence of business harm. Only an explicit, sourced absence of business harm may lower business impact; it must not change priority tiers, relax caps, hide technical findings, or remove independent obligations.

## REQ-010: Include business context

Accept validated business and organization context as data, identify its source and influence, and allow unattended use without questions. Honor a request to skip stored business context. Explain when relevant business or deployment facts remain unknown.

## REQ-011: Look for misuse of business features

An abuse case asks whether an attacker or user can reach a goal in the application from start to end: a technical case rates a path through several weaknesses, and a business case checks a rule of the application's flow. A built-in business case whose question a verified aspect already asks comes after the other built-in cases.

Let users configure abuse-case sources. Include enabled business cases at standard and thorough depth, with at most three model-derived cases at thorough depth. Distinguish confirmed, unproven, mitigated, unresolved, inapplicable, and unchecked cases; create findings only when supported by evidence. An unproven case has evidence that indicates the problem without proving it and stays an unproven, unscored finding. An unresolved case is neither confirmed nor ruled out by the examined code and is not a safe result.

For a single repository, accept repeatable `--abuse-case-file` selections through `assess`, and saved selections through the scan profile's `abuse_case_files` list. CLI selections replace that list. Resolve bounded YAML paths against the admitted repository root without requiring a documentation directory or granting access to host files. Retain automatic discovery at earlier repository locations for compatibility. Explicitly selected files request their enabled cases at every depth, including when the file is also automatically discovered, without loading the cases twice. Preserve case limits and report omissions. Reject unsupported multi-repository file selection and files outside the admitted source boundary.

## REQ-012: Explain what to fix

Explain each finding in developer language: affected location, attack mechanism, harm, and required change. Provide prioritized, system-specific mitigations; urgent actions need concrete steps and verification criteria. State every unresolved decision explicitly.

## REQ-013: Make the report easy to follow

Provide a readable report with consistent finding references, legible architecture diagrams, and detailed catalogs for omitted connections. Show evidenced build-time risks separately, using a table when needed. Highlight up to three unresolved business, design, or deployment decisions and list any further ones with the supporting detail. Do not delegate finding verification to the reader.

## REQ-014: Use results in other tools

Publish Markdown and structured YAML and offer requested HTML, PDF, SARIF, Threat Dragon, and pentest-task exports. Preserve applicable references, requirements results, abuse outcomes, and bounded context provenance. Explain unsupported content and missing export tools.

For the focused AuthNZ review, offer text, JSON and YAML results derived from the same validated report. Reuse the legacy pentest endpoint catalog and task plan with independently selected generic/Strix dialect and JSON/YAML serialization. Preserve evidence status, source locations and requirement references for AuthNZ tasks; identify findings omitted by the existing CWE/evidence filter. Export does not execute or authorize dynamic tests.

## REQ-015: Export without running the analysis again

Allow users to export an existing validated model without rerunning analysis. Apply the format, reference-preservation, and missing-tool rules of REQ-014 to these exports as well.

## REQ-037: Work with an assessment using AI

Expose `review RESULT_DIR` with optional `--with claude|codex` and a model-free `--preview`. Accept a completed private assessment whose recorded artifacts still match their hashes and current model contract, including the supported legacy model basename. Reject incomplete, changed, linked, malformed, or secret-containing results before starting an assistant. Reuse the same validation in exports and the review facts helper. Do not create an export, repeat the analysis, or change the saved result.

Select the assistant from the saved operator profile's exact `claude-cli` or `codex-cli` adapter; `--with` overrides it. API adapters and older state without an adapter require an explicit choice, offered in an interactive terminal. A model or profile name alone cannot establish which coding assistant was used. Require an installed assistant and an interactive terminal for launch; preview starts no process or model call. Display the selected assistant, result directory, and the fact that its own account, model settings, usage charges, and history apply independently of the assessment budget.

Start the interactive assistant with the bundled `review-assessment` skill and references to the existing reports and a validated, read-only query helper. Support evidence-grounded questions and remediation planning with stable finding and repository references. Do not install global skills or follow legacy plugin commands. The helper supports targeted IDs and filters without reading unrecorded requirements sidecars; preserve unavailable requirements context as unknown. The skill distinguishes saved conclusions from proposals and checks source selection and changes before relying on old evidence for a code change.

Use a fresh private working directory so repository or result-directory assistant configuration cannot activate itself. Start Codex with read-only sandboxing and approval prompts, or Claude Code in plan mode with project settings and automatic repository instructions excluded. Repository and result-directory hooks cannot activate at startup; retain native user and managed controls. Keep assistant login and operator configuration external to the report. Never construct shell commands from assessment content or grant permissions from it. Launch authorizes review only; further writes and consequential actions need the user's task authorization and native assistant permission workflow. Bound the external session to four hours and allow cancellation. This handoff is an external assistant session, not the Analyzer's admitted-snapshot execution environment, and offline launch tests do not qualify native assistant enforcement or live behavior.

After a completed assessment, print a shell-quoted `appsec-analyzer review RESULT_DIR` next step without launching it or blocking unattended scans. Preserve existing exit codes, including a completed assessment with a failing policy gate.

## REQ-016: Follow, stop, and resume a run

Let users inspect status, stop a run, and resume compatible interrupted work. Preserve accepted work when resuming and identify stale or incompatible state. A changed Analyzer version alone does not prevent resuming: the run keeps its deadline, limits, recorded costs and elapsed time, and reuses only accepted steps that are still compatible. Store the effective operator profile with the run. On resume, preserve resolved OpenAI alias targets and revalidate their models, options, and prices against the installed catalog; changed definitions or incompatible runtime state require a new run. Expose progress, actionable failure reasons, and recovery steps. Never describe interrupted or incomplete work as complete.

When a full assessment starts without `--resume` or `--rebuild` and its destination holds an unfinished run, an interactive terminal outside CI asks whether to continue that run, start a new scan that reuses its compatible accepted steps, or rebuild. Offer continuing only while the recorded limits, deadline, and accounting permit it; source, settings, and runtime compatibility are still checked when the resume opens. Only an explicit answer selects continuing or rebuilding. Enter, end of input, and repeated invalid answers keep the new-scan default. Noninteractive, quiet, JSON, CI, and followed runs never ask and keep that default. `--resume` without a run in the destination says so instead of reporting unreadable state.

Before full-assessment model analysis, show a compact startup scope with security design, code and configuration as its focus; loaded abuse-case sources; coverage depending on models, context, depth and budget; and exclusions for SCA/CVE scanning, comprehensive secret scanning and runtime testing. Resolve the source summary against the effective settings and admitted snapshot using the analysis's case resolver. Distinguish built-in and organization sources, count enabled repository and explicitly supplied cases without duplication, honor disabled verification and selected case IDs, and exclude rejected definitions and future model-derived cases from startup counts. Loaded definitions are not matched or verified coverage. Keep filenames bounded and safe for terminal display, omit case contents, and fail safely on invalid explicitly selected sources without exposing their contents. Include the same scope in the structured start event; preserve quiet mode and stdout result serialization.
